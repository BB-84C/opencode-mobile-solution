## 0. 总体评价

这套东西的**认证与凭据设计是这个项目最扎实的部分**，明显超出同类个人项目的平均水平：

- 设备与机器凭据只存 SHA-256 哈希，明文仅返回一次（`lib/pairing-store.mjs:357-372`）
- 手机拿到的 Bearer 与后端 Basic 密码完全隔离，密码从不下发（`lib/proxy.mjs:13-24`）
- relay 只绑回环，TLS 交给反代（`relay.mjs:325`）
- 配对码 32 字节随机、只存内存、2 分钟过期、用后即焚（`lib/pairing-store.mjs:338-355`）
- 首次注册的 bootstrap 密钥在第一个 passkey 落盘后自动失效
- frpc 二进制锁定版本并做 SHA-256 校验，校验不过不装（`clients/macos/install.sh:204-234`）
- 撤销设备会同时掐断其活跃 SSE 连接（`relay.mjs:81-87`）
- 日志中剥离 Authorization 头

另外一个设计上的优点，可能你自己没意识到：**`relay/` 的全部路径与参数都是环境变量驱动的**（`relay.mjs:36-43`），没有任何 `/etc` 硬编码写死在逻辑里。这让它可以零代码修改地跑在 macOS 上（见 §5），是一个值得写进 README 的部署模式。

下面是发现的问题，按严重程度排列。

## 1. 🔴 配对设备的 target 授权范围会被静默放大

**位置**：`relay/relay.mjs:215-218` 调用 → `relay/lib/pairing-store.mjs:397-402` 实现

**现状代码**：

```js
// relay.mjs:215-218
function authenticateClient(snapshot, token) {
    const targets = targetRegistry(snapshot);
    return authenticateBearer(snapshot, token)
        ?? passkeyPairing.authenticateBearer(token, [...targets.keys()]);
}

// pairing-store.mjs:397-402
clientFromDevice(device, availableTargetIDs) {
  const dynamicTargets = Array.isArray(availableTargetIDs)
    ? [...new Set(availableTargetIDs.filter((t) => typeof t === 'string' && t))]
    : null;
  const targetIDs = dynamicTargets ?? [...device.targetIDs];   // ← 直接替换
  const targetID = targetIDs.includes(device.targetID) ? device.targetID : targetIDs[0];
```

**问题**：主代理路径把**当前所有可用 target** 传进来，而 `clientFromDevice` 用它**整体替换**了设备自己保存的 `device.targetIDs`，而不是求交集。

**后果**：一台配对时只被授权访问 `windows` 的手机，在 relay 后来接入 `mac` 之后，认证结果会变成 `['windows','mac']`。`/relay/targets` 会列出 `mac`，`X-OpenCode-Target: mac` 能通过 `resolveScope()`。这直接违反 README 中"每个 client 独立 target scope"以及"New phones inherit the targets... pairing never grants broader machine access than that source"的承诺。

**为什么测试没抓到**：`relay/test/passkey-pairing.test.mjs:163` 的用例里，配对源本身就同时包含 `windows` 和 `mac`，替换与交集结果相同，覆盖不到窄 scope 被放大的情形。

**复现**：
1. `tokens.json` 配置两个 target `mac` 与 `work`，配对源 client 的 `targetIDs` 只含 `mac`
2. 用 Dashboard 生成二维码配对一台手机
3. 该手机 `GET /relay/targets` → 会看到 `work`
4. 该手机带 `X-OpenCode-Target: work` 请求 → 通过

**建议修法**（我在本地已应用并验证）：

```js
const targetIDs = dynamicTargets
  ? device.targetIDs.filter((targetID) => dynamicTargets.includes(targetID))
  : [...device.targetIDs];
```

交集同时保留了原本的意图（过滤掉已下线的 target），又消除了放大。三个场景验证：

| 场景 | 设备授权 | 当前可用 | 修复后结果 |
|---|---|---|---|
| target 后来增加 | `['mac']` | `['mac','work']` | `['mac']` ✅ 未放大 |
| 原 target 下线 | `['mac']` | `['work']` | `[]` ✅ 正确拒绝 |
| 未传可用列表 | `['mac']` | `null` | `['mac']` ✅ 无回归 |

修复后 `npm test` 全部 52 项通过。建议补一条窄 scope 的回归测试。

## 2. 🔴 部署脚本的文件属主与 systemd 运行用户不匹配

**位置**：`relay/deploy/deploy-relay.sh:92-97` 与 `relay/opencode-relay.service:7-9`

服务以 `User=ubuntu` 运行，但部署脚本用 `sudo install -m 600` 创建 `tokens.json`，属主为 `root:root`，模式 `0600`。**`ubuntu` 读不到自己的配置文件。**

同样地，`/etc/opencode-relay` 若不是 `ubuntu` 可写，`passkeys.json` 首次落盘会失败；配对设备首次使用时更新 `lastUsedAt` 也会写盘失败。

这不是安全问题，是"照着 README 一步步做，服务起不来，然后排查很久"的问题。建议在脚本里补 `chown`，并在文档里给出期望的属主与权限：

```
/etc/opencode-relay               ubuntu:ubuntu 0700
/etc/opencode-relay/tokens.json   ubuntu:ubuntu 0600
/etc/opencode-relay/passkeys.json ubuntu:ubuntu 0600
```

## 3. 🟠 数据平面没有任何限流、体积与并发限制

**位置**：`relay/relay.mjs:251-323`、`relay/lib/proxy.mjs:13-85`

WebAuthn 与管理 API 有简单的内存限流，但**代理数据通道完全没有**：

- 没有请求体大小上限
- 没有单设备并发连接上限
- 没有全局 SSE 流数量上限

配合 systemd 的 `MemoryMax=128M`，一个泄漏的令牌可以很轻松地把 relay 打到 OOM。建议至少在 README 里给出反代层的兜底配置示例（nginx `limit_req` + `client_max_body_size`，Caddy 对应指令）。

## 3b. 🔴 SSE 流中断时 relay 泄漏上游连接，最终导致 502

**发现方式**：真实设备端到端使用过程中复现，非静态阅读所得。

**现象**：iPhone App 反复重连 `/event` 约 30 次后，该端点开始稳定返回 502，且每次精确耗时 7.8 秒。此时实测连接数：

```
到后端 127.0.0.1:4096 的独立连接：36 条
  其中 35 条属于 relay 进程
relay 自身监听端口 4097 上的真实客户端：约 1 个
```

**判断**：客户端 SSE 流断开后，relay 没有关闭对应的上游连接。每次重连积累一条，直至后端拒绝新连接，表现为 502。

**佐证**：重启 relay 后连接数立即从 36 降至 2，`/event` 恢复正常。后端进程全程健康（`/global/health` 始终 200），可排除后端自身故障。

**根因（已定位到具体一行）**：`relay/lib/proxy.mjs:59`

```js
clientRes.once('close', notifyClose);
```

客户端断开时只调用了 `notifyClose()`，那仅仅更新 `relay.mjs` 里 `activeStreamsByClient` 的登记表（供撤销设备时主动关流使用），**从不销毁 `proxyReq`**。而正确的拆除逻辑本来就写好了 —— 同文件 `close()` 已经做了 `proxyReq.destroy()` 且有 `closed` 标志保证幂等，只是这条路径从未调用它。

**修复（一行）**：

```js
clientRes.once('close', () => {
  if (!clientRes.writableEnded) close();
  else notifyClose();
});
```

判断 `writableEnded` 是为了区分两种 `close`：响应正常结束后也会触发 `close`，那种情况没有东西需要拆，走原来的 `notifyClose()` 即可。

**验证**：本地已实现并三重验证 ——

1. 直接观测上游 `server.getConnections()`：建立 5 条 SSE 后全部中断，连接数 5 → 0
2. 新增回归测试 `relay/test/stream-teardown.test.mjs`，修复前 5 秒超时失败、修复后 311ms 通过
3. 全量套件 53/53 通过（原 52 + 新增 1）

补丁与测试在本地分支 `local/tailscale-relay-fixes` 上，可直接取用。

**附带发现：测试脚手架的连接计数器失效**

`relay/test/helpers/fake-upstream.mjs:14` 用 `request.on('close')` 清理 `eventClients`，但同文件第 9 行的处理器在路由之前已经用 `for await (const chunk of request)` 把请求流读完了。请求流一旦结束，`close` 就已经触发过，之后再注册的监听器不会再收到 —— 该集合**只增不减**。

这有两个后果：一是 `disconnectEvents()` 必须手动 `eventClients.clear()` 才能工作（现有代码正是这么写的）；二是任何想用它断言"连接已释放"的测试都会得到假阴性 —— 我第一版回归测试就因此连续三次误判修复无效。

改为 `response.on('close')` 即可，响应对象在流的整个生命周期内保持打开。已一并修在同一分支上。

**影响**：这是移动端最容易触发的路径——手机锁屏、切换网络、App 进入后台都会断流重连。不修的话，relay 属于「用得越久越必然失效」，且失效表现（502）容易被误判为后端问题。

配合 §3 缺少并发上限，两者叠加会显著缩短故障出现的时间。

## 4. 🟠 上游 Basic 密码明文存盘

**位置**：`tokens.json` 的 `basicPass`；`lib/pairing-store.mjs:511-526` 写入 `passkeys.json` 的机器 Basic 密码

relay 必须用它认证上游，所以无法哈希，这是架构固有约束而非缺陷。但**这意味着 VPS 沦陷等于工作站 opencode 被完全控制**（可读全部代码、执行任意命令）。

建议在 README 的安全章节显式写出这条威胁模型，让部署者在知情前提下决策。当前 README 强调的是"不泄露 token"，读者容易低估这一条。

## 5. 🟠 `/health` 无认证泄露内部拓扑

**位置**：`relay.mjs:220-229`

```json
{"status":"ok","relay":true,"upstream":"127.0.0.1:4096","devices":3}
```

无需任何认证即可获知上游地址端口与已配对设备数量。建议把 `upstream` 与 `devices` 移到需要认证的端点，公开 `/health` 只返回 `{"status":"ok"}`。

## 6. 🟠 CORS 允许任意来源

**位置**：`relay.mjs:240-247`

`Access-Control-Allow-Origin: *` 且允许 `Authorization` 头。这本身不会凭空产生令牌，但一旦令牌泄露，任意网页都可以直接调用 relay。考虑到客户端是原生 App（不受 CORS 约束），这个宽松策略收益有限。建议收紧为 relay 自身 origin，或提供环境变量配置。

## 7. 🟡 passkey 首次注册存在并发窗口

**位置**：`lib/passkey-pairing.mjs:747-800`

`registerOptions()` 检查 `store.canBootstrap()` → 异步生成 WebAuthn options → `registerVerify()` 再次检查 → 异步验证 → 保存 credential。

两个并发注册请求可能都在第一个 credential 落盘前通过 bootstrap 检查。没有全局注册锁，也没有在异步验证完成后再次检查 `hasCredentials()`。

实际利用需要攻击者已知 bootstrap 密钥，风险有限，但修复成本也很低（验证完成、写盘前再查一次）。

---

## 8. 🟡 管理会话没有登出与主动撤销

Web session 12 小时有效、只存内存、没有 logout 端点、没有撤销当前会话的接口。cookie 一旦泄露，在过期前无法止损。`HttpOnly` + `SameSite=Strict` 降低了获取难度，但不覆盖已泄露的情形。

---

## 9. 🟡 配置变更不会关闭受影响的既有流

**位置**：`relay.mjs:81-87`

`closeRevokedStreams()` 只在新配置下 client 无法重新认证时关流。如果 `clientID` 保留但改变了 target、Basic 密码、`targetIDs` 或 directory scope，**既有 SSE 流会继续使用旧连接与旧 Basic 头**，直到某一端主动断开。

后果是"我已经改了密码/收窄了权限，为什么还在生效"。建议在配置变更时比对 scope，对受影响的 clientID 一并关流。

---

## 10. 🟡 目录限制不是文件系统隔离

**位置**：`lib/directory-path.mjs:3-5`

只做字符串规范性检查：不解析 symlink、不访问目标机器确认真实路径、不做"该目录及其子目录"的语义（`allowedDirectories` 是精确字符串匹配）。

这本身可以接受，但 README 用 "Directory scope" 这个措辞容易让人以为是强隔离边界。建议在文档里写清楚它是"传给 opencode 的字符串约束"。

---

## 11. 🟡 状态文件无 fsync、无锁

**位置**：`lib/pairing-store.mjs:26-33`

临时文件 + `renameSync()` 能避免半写文件，但没有 `fsync`、没有多进程锁、没有崩溃恢复日志。断电或文件系统异常时，最近一次的配对、心跳或撤销操作可能丢失。撤销丢失是其中最需要在意的。

---

## 12. 🟡 FRP token 只在启动时读取一次

**位置**：`relay.mjs:46-63`

`readFrpToken()` 在模块初始化时执行。轮换 frps token 后必须重启 relay，否则新机器注册会拿到旧 token。建议在文档里注明，或改为每次注册时读取。

---

## 13. 🟡 不支持 WebSocket

`relay.mjs` 没有 `server.on('upgrade')` 处理。SSE 可用，WebSocket 客户端不可用。当前 App 不需要，但如果未来 opencode 引入 WebSocket 接口，这里需要补。

## 15. 📝 macOS 客户端测试在标准 macOS 上失败

## 16. 📝 README 的 iOS 构建指引不足以装到真机

`app/README.md:6-18` 给出的是 `npm run ios`，而 `package.json` 中该脚本是 `expo start --ios`，只启动开发服务器。由于 `withOpenCodeAppIntents` 配置插件会生成 Swift 并修改 Xcode 工程，**完整功能必须 prebuild 后编译原生包**，不能依赖 Expo Go。

实际可用的路径是：

```sh
npm install
npx expo prebuild --platform ios
npx expo run:ios --device
```

我已在 Xcode 26.6 / Expo SDK 57 / RN 0.86 上验证：prebuild 成功生成 `ios/`，配置插件正确写入 `OpenCodeAppIntents.swift` 并将其加入 App target 的 Sources 编译阶段，URL scheme 正确注册。建议把这三条命令写进 README。

另外值得在 README 中明确：**当前所有 entitlements 都不需要付费 Apple Developer 账号**，免费 Apple ID 的 Personal Team 即可本地安装（7 天有效期）。这对个人使用者是关键信息。

## 17. 一个可能你没考虑过的部署模式（建议写进 README）

因为 `relay/` 完全由环境变量驱动，它可以**直接跑在工作站本机**，配合 Tailscale 取代 VPS + 域名 + FRP：

```
iPhone ──WireGuard──▶ <machine>.<tailnet>.ts.net:8443
                            │ Caddy（原生 Tailscale 集成，自动签证书 + 自动续期）
                            ▼
                      127.0.0.1:4097  relay
                            ▼
                      127.0.0.1:4096  opencode serve
```

我在 macOS 上完整跑通了这条路径，**零源码修改**，只需要：

- 手写一份 v2 `tokens.json`，`targets.mac` 指向 `127.0.0.1:4096`
- `RELAY_PUBLIC_ORIGIN` 设为 `.ts.net` 域名（`validatePublicOrigin` 不限 TLD，`lib/passkey-pairing.mjs:23-33`）
- 不配 `FRPS_CONFIG_PATH`（`readFrpToken` 有 try/catch，缺失返回空串，不阻断启动，`relay.mjs:46-52`）
- `PAIRING_SOURCE_CLIENT_ID` 可以不设（`sourceScope` 未设时取第一个 client，`lib/passkey-pairing.mjs:89-90`）
- Caddy 用 `flush_interval -1`

这条路径的优点：**零公网暴露面、零年费、组件数从 8 降到 4**，而且"VPS 沦陷等于工作站沦陷"这个固有风险直接消失（Basic 密码不出本机）。代价是失去多机器统一路由，且工作站休眠时控制台一并不可用。

对只有一台机器的个人用户，这可能是比 VPS 更合适的默认推荐。

**注意**：TLS 必须用 Caddy 的原生 Tailscale 集成，不能用 `tailscale cert` 写文件再手工挂载 —— Tailscale 官方文档明确说明后者的续期是用户自己的责任，证书 90 天到期后会无预警失效。
