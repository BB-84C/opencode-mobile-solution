# 【2026-09-10 修订】方案 B：Tailscale 取代 VPS —— 现行首选

用户不愿再单独配置 VPS + 域名。核实后确认：**把 relay 搬到 Mac 本机、用 Tailscale 承载传输，可行，且零源码修改。**
下方第 2 节起的原始内容保留为**方案 A（VPS 路线）**，作为备选。

## B.1 架构

```
iPhone (Tailscale) ──WireGuard──▶ <机器名>.tailXXXX.ts.net:443
                                       │ Caddy（自动签证书 + 自动续期 + 不缓冲）
                                       ▼
                                 127.0.0.1:4097  relay（Bearer→Basic，passkey 控制台）
                                       ▼
                                 127.0.0.1:4096  opencode serve
```

砍掉：VPS、域名、frps、frpc、SSH 隧道、机器 OAuth 注册。
保留：passkey 控制台、每设备可独立吊销的 Bearer 令牌、Mac 密码不下发手机、移动端监督界面。

## B.2 代码侧核实结论（读源码所得，非推断）

| 检查项 | 结论 |
|---|---|
| 缺 `/etc/frp/frps.toml` 是否阻断启动 | 不会。`relay.mjs` 的 `readFrpToken` 有 try/catch，返回空串 |
| `.ts.net` 是否通过 passkey origin 校验 | 通过。`validatePublicOrigin`（`lib/passkey-pairing.mjs:23-33`）只要求 HTTPS + 无路径，不限 TLD |
| Linux 路径硬编码 | 无。`TOKENS_PATH` / `PASSKEY_STATE_PATH` / `FRPS_CONFIG_PATH` / `RELAY_PUBLIC_ORIGIN` / `PAIRING_SOURCE_CLIENT_ID` / `PASSKEY_BOOTSTRAP_TOKEN` 全为环境变量 |
| 静态 client 能否作配对模板 | 能。`sourceScope`（`lib/passkey-pairing.mjs:89-102`）在 `PAIRING_SOURCE_CLIENT_ID` 未设时取 `clients` 的第一个 |
| 机器注册流程能否完全不用 | 能。`allocateMachineAssignment` 的 `503 machine_transport_unavailable` 只在该路径抛出 |
| 只起后端、跳过 OAuth/隧道/心跳 | **无需改码**。`opencode-relay-server:197-204` 为四步串联，直接调 `opencode-relay-server-core start backend --json` 即可 |
| relay 绑定地址 | ⚠️ `server.listen(RELAY_PORT, '127.0.0.1')`（`relay.mjs:325`）**写死**，仅端口可配 → 前置反代是必需的 |
| 越权安全问题（原 A 组 A1） | **单 target 下失效**：传入可用列表即 `['mac']`，替换前后同集合。修复降为可选 |

**总改动量：一份 `tokens.json` + 一份 launchd plist + 一份 4 行 Caddyfile。**

## B.3 TLS：必须用 Caddy 原生 Tailscale 集成，不能用 `tailscale cert`

Tailscale 官方文档（`/kb/1153/enabling-https`，Last validated 2025-12-10）明确：

> 对于你用 `tailscale cert` 创建的证书，**续期是你自己的责任**。

Let's Encrypt 证书 90 天到期。手工装文件的方式会在约 3 个月后**无预警失效**。同页给出解法：

> 如果证书是在用户不发起文件安装的情况下被处理的，例如使用 Caddy 的 Tailscale 集成，证书会**自动续期**。

Caddy ≥ 2.5 原生支持：收到 `*.ts.net` 站点的 HTTPS 请求时，直接向本机 tailscaled 索取证书，零配置。

```caddyfile
<机器名>.tailXXXX.ts.net {
    reverse_proxy 127.0.0.1:4097 {
        flush_interval -1
    }
}
```

这一步同时解决：自动签证书、自动续期、SSE 不缓冲。并**绕开了无法查证的问题** —— `tailscale serve` 是否对 SSE 无缓冲，官方文档未说明，采用 Caddy 后无需知道。

前置条件：管理台 DNS 页启用 **MagicDNS** + **Enable HTTPS**。

## B.4 首要风险：与公司 VPN 共存（唯一必须实测项）

Tailscale 官方文档（`/kb/1105/other-vpns`，Last validated 2026-01-12）：

> 理论上可以和其他 VPN 一起用……**但大多数情况下，不做变通是没法共存的。**

三个成因：
1. **激进防火墙规则** —— 多数 VPN 强制全部流量走自己，直接丢弃 Tailscale 包
2. **设备限制** —— **iOS / Android 强制同时只能运行一个 VPN**
3. **IP 段冲突** —— 公司 VPN 若占用 CGNAT `100.64.0.0/10` 则与 Tailscale 直接冲突

对本用户的影响：
- **iPhone 上无法同时开公司 VPN 和 Tailscale**，需来回切换
- Mac 侧变通方案：userspace networking 模式；或在公司 VPN 侧配 split tunnel 放行 `100.64.0.0/10` 与 `fd7a:115c:a1e0::/48`
- Tailscale 默认只接管 `100.x` 流量、不碰默认路由，公司客户端若不激进则可能直接共存
- ⚠️ 使用 exit node 时 split tunnel 变通**失效**（Tailscale 会自设激进规则）。本方案不需要 exit node

## B.5 方案 B 相对方案 A 的代价

- relay 在 Mac 上，**Mac 睡眠时整套失效，包括 passkey 控制台** → 手机丢失时无法远程吊销，须先唤醒 Mac
- 多机器统一路由能力消失（一机一 relay）。当前仅一台 Mac，无损失
- Tailscale 成为新信任依赖。数据为 WireGuard 端到端加密，Tailscale 读不到内容，但控制入网成员
- ⚠️ **机器名会发布到证书透明度公共账本**。签证书前须把 Mac 改为中性名称
- iOS App 自建 + 免费签名 7 天重签，Tailscale 无法改善，仍是最大日常摩擦

## 2. 方案 A 的关键前提：必须另购 VPS

用户现有的"常驻 VPS"是**公司提供的内网接入服务，无管理权限**，不能承载 relay。四个独立的阻断项：

1. 无 root，装不了 systemd 服务
2. 开不了 443
3. 拿不到独立域名与 TLS 证书，而 WebAuthn（passkey）协议**强制**要求 HTTPS 真实主机名，RP ID 从主机名推导，不接受带路径的 origin
4. relay 的本质是把 Mac 上 opencode 的完全控制权（读全部代码 + 执行任意命令）通过隧道暴露出去；落点放在公司资产上属于合规问题

**冲突评估：技术上零耦合。** 两台机器独立，端口/IP/SSH 配置互不相干。`~/.ssh/config` 现有别名 `351`、`Outside`，新增第三个不冲突。iPhone 侧完全无关。

**唯一待实测的摩擦点**：若公司接入服务在 Mac 上是全局模式，Mac 出站 SSH 会绕道公司网络（延迟 + 审计可见）。分流模式则无影响。阶段 A0 实测。

## 4. 架构与暴露面

```
iPhone ──HTTPS/Bearer──▶ VPS:443 Caddy
                              │
                              ▼
                         127.0.0.1:4097  relay（Bearer → Basic 翻译）
                              │
                              ▼
                         127.0.0.1:4100 ◀── frps ◀──SSH隧道──▶ Mac frpc
                                                                  │
                                                                  ▼
                                                        Mac 127.0.0.1:4096
                                                        opencode serve
```

**公网仅开 22 / 80 / 443。**

frps 无需任何公网端口：Mac 主动 SSH 到 VPS 后从隧道内连 frps；relay 本身在 VPS 上，走回环访问 frps 的转发端口。因此 frps 控制端口（7000）与数据端口（4100）均可只绑 `127.0.0.1`。

> 待实测：frp 的 `bindAddr` / `proxyBindAddr` 具体键名与默认值以部署时 `ss -tlnp` 实测为准，不以记忆为准。

## 6. 三个已知坑

### 坑 1：免费 Apple ID 的 7 天期限
App 每 7 天失效，需连 Mac 重签（约 2 分钟）。
**未验证项**：重签后配对令牌（iOS 钥匙串）是否留存。若丢失则须每周重新扫码配对，体验大幅下降。B4 之后专项验证。若确认丢失，$99 付费账号从"可选"升为"值得买"。

### 坑 2：Mac 重启后不自愈
无 launchd、无开机自启、无睡眠唤醒钩子。重启或隧道断开后手机显示离线。C1 解决。

### 坑 3：VPS 被攻破等于 Mac 被攻破
relay 必须持有 Mac 后端密码才能转发，故明文存于 `/etc/opencode-relay/passkeys.json`（0600）。架构固有，非缺陷。
运维要求：该 VPS 不跑其他杂项服务；SSH 仅密钥；定期更新系统。

## 7. 功能边界（代码确认，非推测）

**能做**：浏览全部机器的现存 session、完整对话记录、发提示词并实时流式查看、切换 agent/模型/推理档位（均从目标机器实时拉取）、回答 question、处理权限请求、中断运行（点两次防误触，5 秒内有效）、查看 subagent 子会话、撤销/重做、压缩上下文、重命名、分享、导出。

**不能做（代码明确拒绝，非未完成）**：
- 新建 session —— `mobile-store.ts:824-826`
- fork session —— `mobile-store.ts:901-911`
- 删除 session
- 上传文件（回形针仅插入 `@路径` 引用）
- 实时 diff 浏览（数据层已实现并缓存，界面未接入口）

设计哲学：**手机是监督面板，不是开发机。** 会话的创建与销毁留在 Mac 上。

实际含义：**不能在手机上从零开新任务。** 典型用法是 Mac 上起好会话，出门后用手机盯进度、回答提问、追加指令、必要时叫停。
